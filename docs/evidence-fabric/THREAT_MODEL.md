# Evidence Fabric Threat Model - Secret Redaction

## Objective
Ensure that no sensitive information (secrets) is inadvertently leaked into public engineering cases, recruiter evidence, or other external-facing artifacts generated by the Evidence Fabric.

## In-Scope Secret Types
The system must actively detect and redact the following types of sensitive information:
- API keys (OpenAI, Anthropic, AWS, etc.)
- OAuth tokens
- Bearer tokens
- Private keys (RSA, ECDSA, SSH, etc.)
- Password assignments (`password = "secret"`)
- `.env` values and configurations
- Google service-account secrets
- Email app passwords
- GitHub tokens (classic and fine-grained)

## Redaction Strategy
1. **Value Omission**: The system will *never* print or store the detected secret values in any generated logs, capsules, or public artifacts.
2. **Metadata Logging**: When a secret is detected, the system will only output metadata about the finding:
   - `secret_type`: (e.g., "GitHub Token", "AWS Access Key")
   - `file`: The path to the file containing the secret.
   - `line`: The line number where the secret was found.
   - `redacted`: Always set to `true`.
3. **False Positives vs. False Negatives**: We strongly prefer false positives (redacting benign strings that resemble secrets) over false negatives (exposing real secrets).

## Verification
Automated tests must verify that the redaction engine successfully identifies known mock secret patterns in synthetic data and replaces/omits them in the output artifact, confirming the structural presence of only the `redacted=true` metadata.
